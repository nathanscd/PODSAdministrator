<objective>
Create the `apis/sharepoint-functions/` Python Gen2 codebase skeleton with a fail-closed configuration and secret-provider layer, after a blocking human verification of every new Python dependency.

Purpose: SEC-03 requires the Microsoft client secret and the AES master key to come from Secret Manager and never from the repo, the frontend, or logs. Nothing else in Phase 13 can be built or tested until the package exists, the dependency supply chain is human-verified (research flagged every new pin `[SUS]`), and there is one fail-closed reader for secret references.
Output: `config.py`, `secret_provider.py`, pinned `requirements.txt`, `pytest.ini`, shared `tests/conftest.py`, `tests/test_config_secrets.py`, and the SharePoint reference block in `.env.example`.

Decisions made in-plan (no CONTEXT.md exists for this phase):
- D-13-D (dependency pins): all new Python dependencies are pinned with `==` after the blocking checkpoint; existing repo ranges are kept where a package already exists in `apis/connectivity/requirements.txt`.
- Module naming: the secrets reader is `secret_provider.py` (not `secrets.py`) and the HTTP response helper is `responses.py` (not `http.py`) to avoid shadowing Python standard-library modules `secrets` and `http` in the Gen2 source root.
- Config is a lazy singleton (`get_settings()`), not an import-time singleton: importing the package must never require secret values, but every consumer that needs a secret must fail closed on first use.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Secret Manager → Cloud Functions runtime | Injected secret values cross into process memory; anything that serializes them is a leak surface. |
| pypi.org → build environment | Third-party package code executes in the backend; an unverified pin is arbitrary code execution. |
| Developer machine → repository | Env files, fixtures, and docs can accidentally version real values. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-13-01 | Information Disclosure | `secret_provider.py`, `config.py` error paths | high | mitigate | Errors carry only env-var names; tests assert no secret prefix/suffix appears in exception strings; no `repr()` of values. |
| T-13-02 | Elevation of Privilege | missing secret at startup | high | mitigate | `SecretUnavailableError` raised on absence or wrong key length; no default/generated/hardcoded key path exists anywhere in the module. |
| T-13-SC | Tampering | `python -m pip install -r requirements.txt` | high | mitigate | Blocking-human package-legitimacy checkpoint before any install; exact `==` pins; `[SLOP]` packages forbidden; `msal`/`boto3` excluded from this phase. |
| T-13-02b | Information Disclosure | `.env.example` | medium | mitigate | Names-only block; no `VITE_*` secret entries; values documented as Secret Manager references. |
</threat_model>
