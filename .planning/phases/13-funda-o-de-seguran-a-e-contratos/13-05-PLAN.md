<objective>
Establish the authentication and tenancy boundary: verify the Firebase ID token, derive the tenant server-side, and wrap every SharePoint Firestore access in a store that refuses to cross tenants.

Purpose: SEC-01 requires every backend entry point to be authenticated, and SEC-06 requires tenant isolation to be enforced on the server rather than inferred from what the client sends. Research confirmed no code in the repository ever sets custom claims, and the existing tenant concept is `companyId` on the user profile — so the claim path must exist for the future while the profile read is the working fallback today.
Output: `auth.py` with `AuthContext`, `AuthError`, `extract_bearer_token`, `resolve_auth_context`, `require_firebase_user`; `stores/sharepoint_store.py` with tenant-scoped document access and stable collection-name constants; and two test suites covering authentication and isolation.

Decisions made in-plan:
- Tenant resolution order (D-13-A): verified ID token custom claim `companyId` when present; otherwise `users/{uid}.companyId` read through the Admin SDK; if neither yields a value, raise `AuthError(TENANT_REQUIRED)`.
- Cross-tenant reads return `NotFoundError` (mapped to 404), never a forbidden error, so the store does not confirm the existence of another tenant's document.
- Document ids are namespaced `<companyId>_<logicalId>` and documents also carry a `companyId` field; the store asserts the field matches the resolved tenant on every read, so a mis-keyed document is treated as absent rather than trusted.
- Ordering is contractual: `list_pending_uploads` orders by `createdAt` ascending and then by document id, so two entries persisted in the same millisecond still return in the same sequence on every call. Without the final tiebreaker the listing would be non-deterministic and a retrying client could process the same entry twice or skip one.
- `SharePointStore` accepts an optional Firestore client for tests; production construction uses `firebase_admin.firestore.client()`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client HTTP request → backend identity | Header, body, and query values are attacker-controlled; only the verified ID token is trusted. |
| Tenant A user → Tenant B data | The core isolation boundary of a multi-tenant product. |
| Backend → Firebase Auth | Token verification is the only trust anchor for identity. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-13-17 | Spoofing | `extract_bearer_token`, `require_firebase_user` | critical | mitigate | Strict `Bearer` parsing, `verify_id_token(check_revoked=True)`, all failures collapse to `AuthError(UNAUTHORIZED)` with no echoed input. |
| T-13-18 | Elevation of Privilege | tenant derived from request data | critical | mitigate | Tenant only from verified claim or server-side `users/{uid}` read; no body/query/header path exists; test 4 asserts claim precedence over profile. |
| T-13-19 | Information Disclosure | cross-tenant probe | high | mitigate | Cross-tenant read raises `NotFoundError` (404-equivalent); error text contains neither tenant id nor document key; test 2 asserts this. |
| T-13-20 | Tampering | shared collection with per-tenant filter | high | mitigate | Namespaced doc ids plus stored `companyId` verification on read; `TenantMismatchError` blocks overwriting another tenant's document. |
| T-13-21 | Repudiation | cached identity across requests | medium | mitigate | No module-level `AuthContext`, token, or profile caching; identity resolved per invocation; test 8 asserts fresh objects. |
</threat_model>
