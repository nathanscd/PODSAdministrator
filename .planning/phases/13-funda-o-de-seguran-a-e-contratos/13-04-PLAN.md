<objective>
Replace the single wildcard Firestore rule with an explicit, deny-by-default rule set that preserves today's client behavior exactly, and add the composite indexes the SharePoint queue and audit queries will need.

Purpose: SEC-02 requires least-privilege, default-deny rules. Today the wildcard `match /{document=**}` grants read on every collection to any signed-in user and only masks writes for a small datatem list — so the entire client-visible surface is unintentionally readable, and any newly created collection (including the SharePoint ones Phase 14 adds) is readable the moment it exists. Removing the wildcard without enumerating the live collections would break production screens, so the enumeration is the core work.
Output: a rewritten `firestore.rules` with helper functions and one explicit block per collection; `firestore.indexes.json` extended with SharePoint composite indexes; `tests/test_firestore_rules.py` that verifies both statically (always) and against the emulator (when available).

Decisions made in-plan:
- Behavior preservation is byte-for-byte in effect, not a redesign: collections readable and writable today stay `allow read, write: if signedIn()`; the five datatem-protected collections become `allow read: if signedIn()` with writes denied; `datatemIntegration` and every `sharepoint*` name get `allow read, write: if false`.
- The SharePoint collections are chosen now (not deferred to 14) so the rules file is stable and Phase 14 never edits it: `sharepointSettings` (connection config, one doc per tenant), `sharepointTokens` (encrypted envelopes), `sharepointOAuthTransactions` (short-lived state, nonce and PKCE verifier), `sharepointQueue` (upload intents), `sharepointRateLimits` (fixed-window counters), `sharepointAuditLog` (redacted events).
- Emulator availability is a checkpoint decision, because the repo has no verified Java runtime; the static assertions are mandatory either way and the emulator run is additive evidence.
- Ordering is part of the contract, not an implementation detail: the queue index must be `status` then `createdAt` so the pending-upload query is totally ordered, and every query that reads it appends the document name as the final tiebreaker. Two entries with equal `createdAt` must always come back in the same sequence, otherwise the queue would be non-deterministic for the executor.
</objective>
